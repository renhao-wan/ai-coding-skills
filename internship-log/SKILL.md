# 实习日志

单文件执行手册。格式、保密、素材提炼的细节以用户指定的规则文件为准，这里只管怎么问、怎么写、怎么交付。

## 第一步：确认必需文件与定位

1. **先确认必需输入**。用户没有指定时，逐项询问，不要猜、不要用默认路径：
   - **规则文件**：格式、保密、素材提炼要求的唯一依据，请用户给出路径
   - **日志根目录**：存放 `<公司名>/<年月-岗位>/` 的目录，请用户给出路径
   - **其他必需文件**：当月日志、历史记录等，按上述路径找不到时也要询问用户
2. 读用户给出的规则文件，取当前的格式和保密要求
3. 在日志根目录下找 `<公司名>/<年月-岗位>/` 目录。找不到就报出实际看到的目录结构，请用户确认公司名和岗位写法，不要自己新建
4. 有多个实习目录时问用户写哪一个，不要猜
5. 读当月日志文件，找到最后一条记录，取出它的「待问」和「明天」
6. **逐条核对上一天的「明天」**：开场先问「上次留的这几条，分别完成、没做还是顺延」，这一问可以把几条并列列出来。结果逐条落进今天记录：完成的并入「今日做了什么」，没做的问清是顺延、放弃还是被别的事顶掉，不能默默消失
7. 同时看已有记录的详细程度和写法，新记录保持同一密度，不要突然写长或写短
8. **检查日期是否连续**：上一条记录到今天，中间如果有工作日没写，先问用户是补写、跳过还是只写今天，不要默默接着写
9. 规则文件里有「待完善」一节的，扫一眼：已经有明确结论的，提醒用户可以关掉，但不要自行修改规则文件
10. **看过期待问**：当月日志里超过一周没勾掉、也没出现在最近两天「明天」里的待问，问用户哪些还追、哪些删掉；用户说不管的直接删，不追问理由，也不再提

开场先说一句上次留下的东西，例如「上次留了三条：看心跳日志、反编译 starter、整理下游清单，哪些做了？」，对完再问今天第一个问题。

## 第二步：提问

**一次只问一个问题，等用户回答再问下一个。** 全程控制在 5-8 轮。

必问两项：

1. **今天做了什么**：要求到模块、接口、表这一级
2. **有没有卡住的地方**：按 `现象 → 怎么发现的 → 试过什么 → 根因 → 怎么解决` 一路问下去

追问触发条件：

- 回答笼统，比如「熟悉项目」「参与了开发」「看了代码」：问具体是哪几个模块、哪张表、哪个接口
- 提到问题但没说怎么发现的：问「怎么注意到这个问题的」
- 提到问题但没说排查：问「试过哪些方法，哪个排除了、哪个没排除」
- 提到改法但没说根因：问「最后确认原因是什么」
- 提到技术选型：问「当时还考虑过什么方案，为什么选这个」
- 给出数字：问数字怎么来的，是估算还是实测

**捕获后续承诺**：用户说到「后面再补」「明天问」「下次看」「等有空研究」这类话时，必须记下来，第三步落到「待问」或「明天」，不能只留在正文里。

不必问：感想、评价、累不累、学到了什么道理。「学到什么」只问具体搞懂的技术点。

用户答不上来时，记「未知」，进「待问」，不要替用户补，也不要反复追问同一个点。

用户当天确实没做什么（请假、开会、环境问题没进展）时，如实写简短版本，不要为了凑满五块编内容。

## 第三步：整理

按五块组织：

- `**今日做了什么**`
- `**卡住的问题**`（现象 / 排查 / 根因 / 解决）
- `**学到什么**`
- `**待问**`（勾选框，标归属）
- `**明天**`（最多 3 条）

「卡住的问题」只放真正阻碍进度的；只是还没搞懂、但不影响当天推进的，放「待问」。

如果当天对业务有了新认识，在「今日做了什么」之后加一节 `**业务理解（第 N 版，待验证）**`，版本号在上一版基础上加一，写：谁在用、用来做什么、一条链路怎么走、哪里不确定、有什么权限约束。

### 待问怎么标归属、怎么收口

每条句末标主归属，第二天才知道先找谁：

- `（问 mentor）`：需要人或背景信息才能回答
- `（自查）`：自己翻文档、代码、配置、依赖就能回答
- `（要权限）`：依赖还没拿到的仓库或数据，要写清找谁要、要什么权限

先自查、查不到再问人的，写成 `（自查 + 问 mentor）`，排在前面的表示先走哪条路，不要只并列不排序。

待问是全集，有多少写多少，不设上限。但分两类，处理方式不同：

- **挡路的**：不搞清楚活干不下去，当天或第二天处理，一天通常不超过两条
- **记着就行的**：现在没答案也不影响推进，允许过期

用户说某条不管了，直接删，不追问理由。

### 明天怎么选

「明天」不是待办全集，最多 3 条。从下面三类里挑：

1. 今天明确承诺过的
2. 不解决就会挡住后面工作的
3. 能解锁一批待问的

剩下的事留在「待问」里，不会丢。明天早上打开日志，看「明天」知道先干什么，看「待问」知道还剩什么。

### 整理时做四件事

- 把口语改成书面但不加修饰，保留具体动词和对象
- 代码只留伪代码或 SQL，字段名、表名、常量换成通用叫法
- 用户没说的数字、结果、根因，一律不补
- 没验证过的判断不进「学到什么」：标上「（未验证）」放进业务理解，或当观察放进「今日做了什么」

## 第四步：落盘

- 当月文件不存在就新建：文件名 `<年>-<月>.md`，开头带 H1、「见规则」的引用说明，末尾留 `## 本月小结`
- 新的一天插在当月日志文件最上面：H1 和引用说明之后、已有记录之前
- 标题格式 `### 2026-10-26（周一，第 1 天）`。周几按日期算，第几天从第一天记录往后数，算不准就问用户
- 没有内容的块写「无」，不删标题
- 今天的结论推翻了以往哪天的记录（比如「昨天以为都启动了，实际没有」），在今天正文里点名那一天，不要改历史记录
- 写完把当天这一节展示给用户，问「哪句要改」，等确认
- 不更新 `素材库.md`，那是月底月结才做的事
- 不自动 `git commit`

## 第五步：交付前检查

保密：

- 密码、API Key、token、私服凭证：没有
- 客户姓名、手机号、未公开业务数据：没有
- 内网 IP、内网域名、完整连接串：没有
- 公司代码原文：没有，只有伪代码
- 用户提到把公司相关的架构、流程、术语或代码发到公开仓库、博客、公众号时，提醒先确认是否脱敏

完整性：

- 日期和上一条连续；中间缺失的工作日已经问过用户
- 上一条的「明天」已逐条对过，结果写进了今天记录
- 今天如果推翻了以往某天的结论，已经在正文里点名，读者不会看到两个矛盾版本
- 正文里出现「后面补」「明天问」「下次看」的地方，都已在「待问」或「明天」里有对应条目
- 「待问」每条都标了主归属（问 mentor / 自查 / 要权限），第二路径按先后顺序用 `+` 追加
- 当月日志里超过一周没勾掉、也没进最近两天「明天」的待问，已经问过用户留还是删
- 「明天」不超过 3 条，且每条都能直接执行

质量：

- 「今日做了什么」每条都有具体对象（模块、接口、表），没有「熟悉了项目」「参与了开发」
- 「卡住的问题」有现象、有排查、有根因；缺哪项就写「未知」，不假装解决
- 「学到什么」是机制或结论，不是「学到了很多」「收获很大」
- 「学到什么」里没有未验证的推测；推测都标了「（未验证）」或放进了「今日做了什么」
- 「待问」每一条都是能直接问出口的问句
- 「明天」不是「继续熟悉业务」这类空动作
- 详细程度和本月已有记录接近，没有突然膨胀

## 禁止

- 不编数字、不编结果、不替用户下结论
- 不写「提升了系统性能」这类没有对象的空话
- 不贴大段代码
- 不把一天的记录扩写成散文
- 用户回答简短时不追问超过两轮，避免变成审问
- 不读公司代码仓库，日志只依据用户口述；需要技术细节时请用户描述，不要自己去翻代码
