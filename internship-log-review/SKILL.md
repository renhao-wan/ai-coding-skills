# 实习日志审核

单文件执行手册。**只读，不改文件，不提交。** 检查标准以用户指定的规则文件为准，本文件只规定查哪些维度、怎么输出。

## 第一步：确认输入与范围

1. 确认三份输入，逐项向用户要路径，不要猜、不要用默认路径：
   - **规则文件**：检查标准的唯一依据
   - **当月日志**：被审核的对象
   - **写日志用的 skill**（internship-log）：流程层面的依据
2. 确认范围，按用户给的参数：
   - 无参数：审日志目录下最新月份的日志文件
   - 给年月（如 `2026-10`）：审该月
   - `today`：只审最新一条记录
3. 读日志前先看行数。超过 600 行，派一个只读 subagent 执行第二步和第三步，交代清楚三份输入路径、审核范围、只读要求；不超过就在当前对话里做
4. 审单日时，额外读上一条记录，用于核对收口和术语一致；日志里只有一条记录时说明无法比对
5. 用户要求审 `today` 但最新一条不是今天，直接说明实际是哪天、今天还没写，不拿旧记录凑数

## 第二步：按五个维度检查

每条标准都现场从规则文件读，本文件不复述条款内容。

**结构**：对照规则里讲每天写什么、业务理解怎么记的部分，以及 internship-log 第四步。查块的完整性和顺序、标题格式、日期顺序、版本号、旧内容是否被误删。另外查日志里的 `[[...]]` 链接是否指向日志目录 `主题笔记/` 下真实存在的文件，悬空链接要报。

**内容**：对照规则里讲每天写什么的部分，以及 internship-log 第二、三步。查每块有没有具体对象、四要素是否齐、结论是否超出证据、待问能否直接出口并标了归属、明天能否直接执行。再查技术细节是否该外置却堆在日志里（类名 / 接口路径 / 参数 / 错误码 / 缓存 key / commit 等成串出现），已外置的日志是否只留「做了什么 + 结果」+ 链接。

**跨天**：对照规则里讲待问怎么收口的部分，以及 internship-log 第一步。查上一条的「明天」是否逐条收口、推翻旧结论是否点名、过期待问是否处理、术语和缩写前后是否一致。审单日时，过期待问跳过。

**保密**：对照规则里讲保密的那部分逐条比对，再看代码是否只到伪代码、提到公开发布时是否确认脱敏。

**技术自洽**：不依赖规则，通读判断。查数字和枚举对不上、同一概念两种叫法、因果不成立、改法描述有歧义。这一项靠通读，不能靠清单。

整月审核时，日志末尾如果有本月小结，按规则里讲月结和素材库的部分单独核对，不套用上面按天的维度。

## 第三步：输出

第一行标明范围，然后固定四段：

```
审核范围：2026-10 整月 / 2026-10-28 单日

## 必须改
## 建议改
## 可选
## 已通过
```

每条问题写成三项：

- `[行 N]` 问题是什么，会造成什么误解
- 依据：规则或 internship-log 的具体节名
- 建议：怎么改。只指出方向，不替用户补他没说过的事实

「已通过」必须有，列出查过且没问题的项；跳过的项单独注明「未检查」及原因。

## 约束

- 只读，不改文件，不 `git commit`
- 不补用户没说过的事实、数字、根因
- 没问题就明确写「通过」，不为了显得有用而挑刺
- 每条必须带行号和依据，不能只说「感觉不对」
- 同一个问题只报一次，不换个说法重复
- 只查事实、规则符合度和自洽性，不评价文笔；规则明令禁止的空话要报，个人偏好不报
- 不读公司代码仓库，判断只依据日志和规则文件
